# Cryptography

Everything here is implemented once, in `crates/core`. Clients call it and never reimplement it.

## Primitives

| Purpose | Primitive |
|---|---|
| Password stretching | Argon2id, version 0x13 |
| Key derivation | HKDF-SHA256 (RFC 5869), empty salt |
| Symmetric encryption | XChaCha20-Poly1305 (24-byte random nonce, 32-byte key, 16-byte tag) |
| Key wrapping to a user | HPKE (RFC 9180), **auth mode**, suite DHKEM(X25519, HKDF-SHA256) / HKDF-SHA256 / ChaCha20Poly1305 |
| Hashing, fingerprints | SHA-256 |
| Randomness | OS CSPRNG (`getrandom`; `crypto.getRandomValues` in WASM) |

Implementation crates (RustCrypto / dalek ecosystem): `argon2`, `hkdf`, `sha2`, `chacha20poly1305`,
`hpke`, `x25519-dalek`, `getrandom`, `zeroize`, `unicode-normalization`. All key material is zeroized on drop.

## Encoding conventions

- Binary values in JSON: **base64url without padding**.
- IDs (users, memos, attachments, devices): **UUIDv7**, generated by the client. In JSON, lowercase
  hyphenated strings. Inside AAD/HPKE `info`, the 16 raw bytes.
- Integers inside AAD/`info`: big-endian, fixed width (`u8`, `u32`, `u64` as stated).
- Labels: ASCII strings, followed by a single `0x00` byte.
- Timestamps: Unix milliseconds (`i64`).

## Symmetric envelope

Every symmetric ciphertext in the system uses this layout:

```
envelope = format:u8 (0x01) || nonce:[24] || ciphertext || tag:[16]
aad      = format:u8 (0x01) || label || 0x00 || context
```

Each nonce is fresh random. Decryption fails closed: on any error, show "cannot decrypt" and never
show partial plaintext.

| Purpose | Key | Label | Context |
|---|---|---|---|
| Account key, password copy | `master_key` | `memo/v1/account-key` | `user_id` |
| Account key, recovery copy | `recovery_wrap_key` | `memo/v1/account-key-recovery` | `user_id` |
| User private key | `account_key` | `memo/v1/private-key` | `user_id` |
| Vault | `account_key` | `memo/v1/vault` | `user_id`, `version:u64` |
| Memo payload | `memo_key[key_version]` | `memo/v1/memo` | `memo_id`, `version:u64`, `key_version:u32` |
| Attachment original | `attachment_key` | `memo/v1/attachment` | `attachment_id`, `kind:u8 = 0` |
| Attachment thumbnail | `attachment_key` | `memo/v1/attachment` | `attachment_id`, `kind:u8 = 1` |

Putting `version` into the memo AAD means the server cannot present an old ciphertext as a newer
version. Clients also refuse any memo version lower than the highest they have seen for that memo.

## Key hierarchy

```
password ──Argon2id(salt)──► stretched ──HKDF──┬─► auth_key     → sent to the server, which stores a hash
                                               └─► master_key   ─┐
recovery_key ──HKDF──┬─► recovery_auth_key → server stores a hash│ both wrap
                     └─► recovery_wrap_key  ─────────────────────┤
                                                                 ▼
                                                           account_key (random, permanent)
                                                             ├─► X25519 private key (permanent)
                                                             └─► vault

memo_key[key_version] (random per memo, rotated on revocation)
   ├─► HPKE-wrapped to each member's public key, sender = memo owner
   ├─► memo payload (body + attachment references)
   └─► attachment_key per attachment (stored inside the memo payload)
          └─► attachment original + thumbnail
```

The account key and key pair never change during the account's lifetime. A password change or recovery
only re-wraps the account key, so all memo keys and contact pins stay valid. Because a user's public
key never changes, **a changed public key always means something is wrong** (see *Contact keys*).

### Password-derived keys

```
pw        = UTF-8(NFC(password))
stretched = Argon2id(pw, salt:[16], m, t, p, output = 32 bytes)
auth_key   = HKDF-SHA256(ikm = stretched, info = "memo/v1/auth",   L = 32)
master_key = HKDF-SHA256(ikm = stretched, info = "memo/v1/master", L = 32)
```

- `salt` is 16 random bytes, generated by the client at registration and at every password change.
- Default parameters: `m = 65536` KiB (64 MiB), `t = 3`, `p = 1`.
- **Clients enforce bounds on the parameters the server sends.** They refuse `m < 65536`, `t < 3`,
  `p < 1` (this blocks a downgrade by a malicious server, which would make the password cheap to
  brute-force from `auth_key`). They also refuse `m > 1048576`, `t > 20`, `p > 8` (prevents a
  denial of service).
- Clients require passwords of at least 12 characters.

The server stores `auth_hash = Argon2id-PHC(auth_key)` with its own random salt and light parameters
(`m = 19456`, `t = 2`, `p = 1`). The input is already high-entropy, so this hashing only ensures that a
leaked database cannot be used to log in directly.

### Recovery key

32 random bytes, shown **once** at registration (and after each recovery). The client asks the user to
re-enter it before continuing.

```
recovery_auth_key = HKDF-SHA256(ikm = recovery_key, info = "memo/v1/recovery-auth", L = 32)
recovery_wrap_key = HKDF-SHA256(ikm = recovery_key, info = "memo/v1/recovery-wrap", L = 32)
```

Display format: `recovery_key || SHA-256("memo/v1/recovery-checksum" || 0x00 || recovery_key)[0..3]`
(35 bytes), Crockford Base32 encoded (56 characters), shown as 14 groups of 4. Parsing is
case-insensitive, ignores spaces and hyphens, and maps `I`/`L` → `1` and `O` → `0`. A checksum
mismatch is reported as a typo.

### User key pair

An X25519 key pair is generated at registration. The private key is stored on the server as an envelope
under `account_key`. After decrypting it, a client **recomputes the public key and compares it with the
one the server holds**. A mismatch is a hard error.

## Memo keys and sharing

Each memo has a sequence of 32-byte random keys, numbered by `key_version` starting at 1. The owner's
client wraps each key for each member with HPKE:

```
mode   = mode_auth (0x02), skS = owner's private key, pkS = owner's public key, pkR = member's public key
info   = "memo/v1/memo-key" || 0x00 || memo_id || key_version:u32 || owner_id || member_id
aad    = empty
pt     = memo_key (32 bytes)
wrapped_key = 0x01 || enc:[32] || ct:[48]                       (81 bytes)
```

Auth mode lets a member verify that the key really came from the memo's owner. Without it, a malicious
server could invent a memo key, wrap it for you, and slip a fake "shared" memo into your account.
The owner wraps keys for themselves the same way (`member_id = owner_id`).

A public key that is a low-order point makes the key agreement fail. The server rejects such keys at
registration, and a client that is given one reports an error instead of wrapping.

**Members verify every received key.** They open the HPKE with the **pinned** public key of
`owner_id`. If it fails, the memo is not shown, and the user sees a warning naming the owner.

Operations (HTTP details in [api.md](api.md)):

- **Create:** the client generates `memo_key[1]` and wraps it for itself.
- **Share:** only the owner can share. The owner looks up the recipient's public key (pinning it, see
  below) and wraps **every existing** `key_version` for them, so they can read the history. The
  client also records the recipient in the vault (`shares`, see *Vault payload*). This record, not the
  server's member list, says who the owner gave access to.
- **Change permission:** no cryptography. The server enforces it (see threat-model limitation 2).
- **Revoke:** the owner's client generates `memo_key[n+1]`, re-encrypts the current payload as a new
  version under it, and wraps it for the remaining members. A remaining member must be listed by the
  server **and** recorded in the owner's vault (`shares`), with a pinned key equal to the one the
  server presents. If the server lists someone the vault does not know, the client refuses: the owner
  removes that user in the same step (or, if another of their devices just shared the memo, syncs
  first). So a server cannot get a memo key by adding itself to a member list. The revoked users are
  removed from `shares`. The server applies all of this atomically. Old key versions stay with the remaining members so they
  can read history. Attachment keys live inside the payload and are **not** rotated: a former member who
  kept an old payload could decrypt attachments they could already see, but the server refuses to serve
  them any blob.
- **Leave:** a member removes their own access. No rotation happens, since they leave voluntarily,
  and the owner's `shares` record of them stays. The server stops sending them the memo. The owner
  can still rotate afterwards by removing them.

## Contact keys (trust on first use)

When a client first needs another user's public key (sharing to them, or verifying a memo they
shared), it takes it from the server (`GET /users/lookup`, or the member list of an `access` change)
and **pins** it in the vault together with the username.
The vault syncs, so all of a user's devices share the same pins.

If the server later returns a different key for a pinned user, the client treats it as an attack:
it refuses to share with or accept keys from that user and shows a prominent warning. Since user key
pairs never change, there is no legitimate reason for this to happen.

Pins are kept per user id, but people choose each other by name. Usernames are unique and never
change, so a **pinned username that appears under another user id** is handled the same way: the
client does not pin it, does not share with it and does not accept keys from it. Members are shown
under the username they were pinned with.

Fingerprint, for out-of-band verification:

```
fp = SHA-256("memo/v1/fingerprint" || 0x00 || user_id || public_key)[0..16]
```

It's shown as 32 lowercase hex characters in 8 groups of 4. Users compare it in person or over another
channel. Once they confirm, the client marks the contact `verified` in the vault.

## Plaintext payloads

JSON payloads are padded before encryption to hide exact sizes:

```
plaintext = len:u32 || json_bytes || 0x00 * k        (total length is a multiple of 256)
```

Clients ignore unknown fields. `v` increases on incompatible changes. A client that sees a `v` higher
than it supports shows the memo **read-only** and never rewrites it. A vault with a higher `v` is not
decoded at all, because the client would rewrite it on the next contact pin. The client asks the user
to update instead.

### Memo payload

```json
{
  "v": 1,
  "body": "# Groceries\n- milk\n\n![](attachment:0192f3c4-7a1b-7c2d-9e8f-0a1b2c3d4e5f)",
  "edited_at": 1761480000000,
  "attachments": [
    {
      "id": "0192f3c4-7a1b-7c2d-9e8f-0a1b2c3d4e5f",
      "key": "<base64url, 32 bytes>",
      "mime": "image/jpeg",
      "size": 2412331,
      "width": 4000,
      "height": 3000,
      "thumb": { "mime": "image/webp", "width": 512, "height": 384 }
    }
  ]
}
```

- `body` is CommonMark (plus tables, strikethrough and task lists). Clients that render it display a
  single newline as a line break.
- Tags are `#hashtags` in the body: `#` followed by letters, digits, `_`, `-` or `/`, with at least
  one character that is not a digit (`#2024` is not a tag). The `#` starts a line or follows
  whitespace or `(`. Tags inside code spans and fenced code blocks do not count. They compare
  lowercased. `memo_core::text` implements this, so every client agrees.
- Images are referenced as `attachment:<id>` URLs. `thumb` is `null` if no thumbnail exists.
- Links to other memos are `memo:<id>` URLs: `[Groceries](memo:0192f3c4-…)` or `<memo:0192f3c4-…>`.
  They open only for members of the target memo. Clients list a memo's backlinks (the memos linking
  to it) from what they can decrypt; the server never sees links.
- `edited_at` is the client's clock when the edit was made. It is for display only.

### Vault payload

```json
{
  "v": 1,
  "contacts": {
    "<user_id>": { "username": "alice", "public_key": "<base64url>", "pinned_at": 1761480000000, "verified": false }
  },
  "settings": {},
  "shares": { "<memo_id>": ["<user_id>"] }
}
```

- `shares` lists, for each memo the user owns and shared, the users they shared it with. It is left
  out when empty. Clients read it when they revoke (see *Memo keys and sharing*).

- `settings` keys starting with `filter/` are saved filters, one key per filter (`filter/<uuid>`), so
  two devices can add filters at the same time:
  `{"name": "Open work", "query": "", "tag": "work", "has": ["open_tasks"]}`. `has` lists what a memo
  must contain: `tasks`, `open_tasks`, `links` (web or memo links), `images` or `code`. Clients skip
  filters they cannot parse.

## Attachments

Each attachment gets a random 32-byte `attachment_key`. The original and the optional thumbnail are
encrypted as separate envelopes (`kind` 0 and 1) with no padding. The server only ever handles them as
opaque `application/octet-stream`.

Clients, before encrypting:

1. **Allowlist:** `image/jpeg`, `image/png`, `image/webp`, `image/gif`. Clients detect the type from
   magic bytes, not the file name. HEIC/HEIF is converted to JPEG on the device. Anything else is
   rejected for now.
2. **Strip metadata by default** (EXIF, XMP, IPTC, PNG text chunks). If EXIF orientation is not 1,
   the image is re-encoded with the rotation applied. Otherwise metadata is removed without
   re-encoding.
3. **Downscale** (default on for Android): longest side at most 2560 px.
4. **Thumbnail:** WebP (JPEG as fallback), longest side 512 px. GIFs use their first frame.

When rendering, clients check the decrypted bytes against the `mime` in the payload. Anything that
does not match, or is not on the allowlist, is offered as a download and never rendered inline. SVG
and HTML are never rendered. The web client renders through `Blob` URLs with the explicit type.

**Rendering bodies** (`memo_core::render`: HTML for the web and desktop clients, a block tree for
Android's native UI): raw HTML in a body is shown as text; links are kept only for `http`, `https`
and `mailto` and open with `rel="noopener noreferrer"`; images load only from `attachment:` URLs,
and remote images become links, so opening a memo never contacts a third party. The page's CSP
blocks inline scripts as a second line of defence; Android never uses a web view for memos.

## Account flows

**Register** (needs an invite code):
1. The client generates `user_id`, `salt`, `account_key`, the X25519 key pair and `recovery_key`.
2. It derives `auth_key` and `master_key`, then `recovery_auth_key` and `recovery_wrap_key`.
3. It sends `POST /auth/register` with: `user_id`, `username`, KDF parameters, `auth_key`,
   `recovery_auth_key`, `public_key`, `enc_account_key`, `enc_account_key_recovery`,
   `enc_private_key`, an empty vault envelope (version 1), the invite code and the device name.
4. It shows the recovery key and requires the user to confirm it.

**Log in:**
1. `POST /auth/prelogin {username}` returns `{salt, m, t, p}`. For unknown usernames the server
   returns a deterministic fake salt (`HMAC-SHA256(server_secret, "prelogin" || username)[0..16]`)
   and the default parameters, so the endpoint cannot be used to find out which usernames exist.
2. The client checks the parameter bounds, then derives `auth_key` and `master_key`.
3. `POST /auth/login {username, auth_key, device}` returns the device token, `user_id`, `public_key`,
   `enc_account_key` and `enc_private_key`.
4. The client decrypts the account key, then the private key, and checks the public key matches.

**Unlock without a password (native):** after a login, the device token, `account_key` and private key
are stored in the OS keystore (Android Keystore-wrapped storage; on Linux the Secret Service via the
`keyring` crate). If no keystore is available, the client asks for the password at every start.
On the desktop, *Lock* signs the device out and deletes the stored keys and token; the local database
stays, and unlocking is a new login (online) that reopens it. Only signing out deletes it.

**Web session:** keys live in memory only. An optional "keep unlocked in this browser" setting (off by
default) wraps `account_key` with a non-extractable WebCrypto AES-GCM key kept in IndexedDB.

**Change password:** the client re-authenticates with the current `auth_key`, then sends a new salt,
KDF parameters, `auth_key` and `enc_account_key`. It can optionally revoke all other devices.

**Recover** (forgotten password):
1. `POST /auth/recover {username, recovery_auth_key}` returns `enc_account_key_recovery`,
   `public_key` and `enc_private_key`, plus a single-use `recovery_token` valid for 10 minutes. This
   endpoint is strictly rate-limited.
2. The client decrypts `account_key`, then the private key (checking it against the public key),
   picks a new password and generates a **new** recovery key.
3. `POST /auth/recover/complete` with the new password material and the new recovery material. The
   server revokes all devices and invalidates the old recovery key. The client shows the new recovery key.

## Test vectors

`crates/core` generates JSON test vectors (`docs/test-vectors/`) for every derivation, envelope,
HPKE wrap, payload encoding and recovery-key encoding. The WASM and Android builds run the same vectors
in CI, so all platforms are guaranteed to produce byte-identical results.
